# ShivaCore M1.2 — VMM Implementation Baseline

**Specification:** `SC-SPEC-001-REV2.1-M1.2-VMM-A`  
**Status:** `IMPLEMENTATION-HARDENED / CONDITIONAL PASS`  
**Target:** x86_64, 4-level paging, UP/BSP-only

## Implemented in the current branch

The VMM validation core in `kernel/src/vmm.rs` now enforces the following fail-closed invariants before hardware page-table mutation:

- canonical x86_64 virtual addresses
- half-open userspace interval `[0x0000_0000_0001_0000, 0x0000_8000_0000_0000)`
- checked `ptr + len` arithmetic
- 4 KiB physical-frame alignment
- 48-bit physical-address baseline
- W^X (`writable && executable` is rejected)
- user mappings only inside the exact userspace interval
- HHDM restricted to supervisor/RW/NX policy
- level-specific x86 bit-7 semantics
- bounded bootstrap physical-to-virtual translation

## Page-table level semantics

The implementation treats bit 7 according to the actual x86-64 page-table level:

| Level | Bit 7 |
|---|---|
| PML4 | not PS |
| PDPT | PS (1 GiB huge page) |
| PD | PS (2 MiB huge page) |
| PT | PAT |

M1.2 baseline does not support huge pages. Therefore PS is rejected at PDPT and PD only. Bit 7 at PT is not interpreted as PS.

## Userspace policy

A mapping carrying the User bit is valid only when its virtual address is inside:

```text
[USER_SPACE_BASE, USER_SPACE_TOP_EXCLUSIVE)
```

Checking only `virt < HHDM_BASE` is insufficient because other supervisor/kernel virtual ranges may exist below the HHDM window.

## HHDM policy

The HHDM window is:

```text
[HHDM_BASE, HHDM_END)
```

HHDM entries must be:

- Present
- Writable
- Supervisor-only (`User=0`)
- NX

HHDM is therefore not a userspace mapping and is never executable.

## Hardware page-table mutation and transactional rollback (2026-10-08)

`kernel/src/vmm.rs` now provides `HardwareMapper`, the real PML4 → PDPT → PD → PT
hardware mapping path with entry programming:

- The full M1.2 validation/policy layer runs fail-closed **before the first
  frame allocation** (W^X, exact userspace interval, canonicality, HHDM
  supervisor/RW/NX, level-specific PS semantics).
- `map_page` descends the 4-level hierarchy, allocating, zeroing and wiring
  intermediate tables on demand (`Present | Writable`, plus `User` only for
  user mappings — x86 requires the user bit on all levels).
- Allocation is **transactional** (`MapJournal`): every intermediate frame
  allocation and every entry write is journaled; on any failure the walk rolls
  back all writes to their original values and frees all newly allocated
  tables in reverse order. Double-mapping is rejected (`AlreadyMapped`)
  without leaking frames.
- Physical memory access is abstracted behind `FrameBackend`
  (alloc/free/read/write, fail-closed). Boot integration (HHDM translation +
  BootInfoFrameAllocator, CR3 install, TLB maintenance) follows in the
  hardware chain step of the P0 acceptance chain.

Regression evidence: 8 new tests including mid-walk rollback (frame
exhaustion after partial descent), hierarchy reuse, huge-page rejection
during walk, and no-leak-on-validation-failure. `cargo test -p shivacore vmm`
is 17/17.
